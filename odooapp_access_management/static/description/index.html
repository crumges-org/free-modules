Odoo Access Management

Advance Access Management gives you complete user access rights and role based access control in one app. Restrict menus, models, fields, records, buttons, search and chatter per user, group or profile. Every access restriction is applied on the server, so it also applies to the API.

Guided 4-step setup 31 ready-made presets Server-side enforcement Rule explainer JSON import / export 6 languages

Access rights enforced on the server

Field and record restrictions are applied in read, fields_get and the ORM access layer, not only in the view. XML-RPC and web_read return the same restricted data as the browser.

Every access restriction is explained

Pick a user and a model. The Access Explainer lists each effect, the rule that caused it, and how that rule reached the user (profile, group or direct). Odoo's own access rights and record rules are included in the same report.

Access rules portable between databases

Rules export to JSON using external IDs and technical names, not database ids. Import runs a dry run that lists any reference missing from the target database before writing anything.

Guided access management setup in four steps

Configuration > New Restriction walks you through it: pick the users or groups, pick the models and menus, choose what they can do, then read a plain-language summary of exactly what will be created before anything is written. No knowledge of the underlying rule structure is needed.

Step 1 · Who

Users or groups. The count of people affected updates as you choose, and administrators are flagged before you go further.

Step 2 · What

The models it covers and the menus to hide. Either on its own is enough.

Step 3 · Restrict

View only, cannot delete, cannot create or delete, or your own combination. Then fields, records, chatter, search, buttons and account-wide switches.

Step 4 · Review

A written summary of what will be created, then apply. Optionally save it as a reusable profile at the same time.

“Only their own records” is resolved per model rather than assumed: the wizard looks for the model's own salesperson or responsible-user field and writes the matching domain. A model with no link to a user gets no domain instead of a broken one.

What comes out is an ordinary Access Rule, editable in full afterwards. The wizard can also load an existing rule back in — and when a rule has grown past what the four steps can show, it says so and sends you to the rule form rather than silently dropping the difference.

31 ready-made access control presets

Most setups need no custom rules. Open the Preset Library, search by name or by the model you want to restrict, select one or more presets and apply. Each becomes a profile with its rules already configured, editable like any other profile.

Cross-app · Read-only Auditor, External Contractor, Contact Data Privacy Sales & CRM · Own Records, Fixed Pricing, No Lead Export Inventory & Manufacturing · Warehouse Operator, Read-only BoM Accounting · No Delete, Viewer, No Bank Details HR, Project, POS, Helpdesk · Self-Service, Own Tasks, Own Tickets

Presets that need an app you have not installed are marked unavailable. The wizard lists which models it will apply to and which it will skip on your database before you confirm.

Access management that cannot lock you out

  • Administrators are excluded from all rules unless you enable a system parameter.
  • A global kill switch disables every rule at once.
  • Saving a rule that would lock out its own author is blocked at save time.

What this Odoo access management app controls

Odoo menu access rights and model access control

  • Hide any menu, with or without its sub-menus
  • Block create, read, edit or delete per model
  • Set a model read-only
  • Hide Archive, Duplicate, Export, Import, Print, Insert in Spreadsheet, or the whole Action menu

Odoo field access rights

  • Invisible, read-only or required
  • Remove the internal link, quick create and "Create and edit"
  • Exclude a field from exports while keeping it visible
  • Apply any of the above conditionally, based on the record

Record level access rights and domain restrictions

  • Any domain, applied per operation
  • Read, write, create and delete configured independently
  • Relational and hierarchy fields supported
  • Soft restrict: filter a model in its own views without emptying it where other records reference it

Sensitive data masking

  • Full, partial, email, phone or a custom pattern
  • Applied in read, so exports and API calls return the masked value
  • Example: phone shows the last four digits, email keeps the domain

Button, tab and search access rights

  • Hide header buttons, notebook pages and kanban links
  • Hide named filters and group-bys
  • Hide the custom filter, favourites or the whole search panel
  • Global or per model

Chatter access rights

  • Six independent switches: whole chatter, Send Message, Log Note, Activities, Followers, Attachments
  • Allows read-only chatter, where history is visible but posting is not

Time based access management and expiring rules

  • Rules active only inside a time window, with a timezone
  • Start and end dates per rule
  • Automatic revocation on expiry, with a scheduled cleanup

User account access control

  • Password expiry with warning emails at 7 days and 1 day
  • Audited login as another user, and force logout
  • Read-only user, developer mode off, module install blocked
  • External API access restricted per user

How conflicting access rules resolve

Deny wins. Booleans are combined with OR, hidden sets with union, domains with AND.

Priority breaks ties between restrictions of the same kind. It cannot turn a denial into a permission. The Explainer lists every rule that contributed to a result.

Performance

All rules that apply to a user are compiled once into a single policy, cached per user, company, language and debug mode. Each enforcement point is then a dictionary lookup.

Time-based rules are evaluated separately so they do not invalidate the cache. The cache is cleared when a rule, profile or assignment changes.
